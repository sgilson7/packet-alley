# Plan

Each decision, and the words in the brief it answers. Approved in advance
(BRIEF.md, Autonomy).

| # | Decision | Answers |
| --- | --- | --- |
| P1 | A level is a small network (nodes, cables, programs) plus the changes a student may make, its goals, a lesson and one quiz question. A run is decided in full the moment it starts (`Sim::build(level).run(ticks)`) and the page plays the recorded frames back; the same level and seed give the same run on every machine. | "networking challenges", "visualizes packets moving" |
| P2 | Time is whole ticks. Each tick: programs send, frames that arrive are handled by the node they reach, then each port puts one frame on its cable. Every crossing of a cable is a recorded `Transit`; the page interpolates a packet's position along it. | "visualizes how packets move" |
| P3 | Devices: host/printer/server (one cable, one address), hub (repeats to all, so two at once collide), switch (learns a MAC per port, floods the unknown), router (forwards by longest-prefix match, decrements TTL). The link layer, then the network layer. | "switching out a hub with a switch", "make a network more efficient" |
| P4 | The student changes the network through a level's `edits`: an address, a device's kind, a gateway, a route's next hop, a blocked cable, an app's TCP fields, a window and timeout. The core applies the edit and refuses a bad one; nothing else is editable. | "make changes to a network" |
| P5 | Three teaching chapters — link, network, transport — each with a short intro set (one idea, one or two choices: address a packet; hub vs switch; a switching loop; a gateway; a routing table; a TTL loop; ARP; the three-way handshake; go-back-N) and an advanced follow-up set (see P13). | "networking challenges for students", "creating a loop" |
| P6 | Teaching tool as well as game (the BT Lab): every level names the idea it teaches and why a loss happened (a diagnosis from the drop events), a device inspector shows what a switch or router actually knows, and passing opens one quiz question for a third star. Three stars: pass, answer right, meet the bonus. | "both a teaching tool and a game" (Sam) |
| P7 | Progress (stars per level, teacher mode) lives in the browser (`localStorage`), written and read by the core as JSON. An unreadable save is a new player, never an error. Levels unlock one at a time; teacher mode unlocks all. | levels must mean something between visits |
| P8 | Every reader-visible string is in `data/copy.json`; every level, network and quiz in `data/levels.json`; playback speeds in `data/display.json`. The core returns copy keys for events and every number the page draws. The page holds no numeric literal but 0 and 1. | Builder D3, D5 |
| P9 | Accessibility: every packet carries a letter and is named in a legend, every map mark is a symbol (✓ ✕ ✻ + ·), and the status palette is Okabe–Ito, so nothing is told apart by colour alone. The log states each step in words. | "accessible and colour-blind friendly" (Sam) |
| P10 | Art: TikZ through the pipeline from Level Twenty / Raiders of the Lost Mart (`tools/art*.py`, `artlib.py`): device icons, chapter backdrops and a title, in the look of `Sam_Comm_final.png`. Icons read by silhouette, checked in greyscale. | "use the tikz latex prompt", "sam comm final as an inspiration" |
| P11 | The **interactive** denial-of-service / flooding mechanic is **not built**. Sam's safeguard was met by design (in-game gadgets, a fixed list of made-up source addresses, an I/O-free core that can emit nothing), but automated safety review stopped the build on it three times, and a safety stop is answered by leaving the feature out and saying so, not by disguising it. Recorded in BRIEF.md, README.md and SECOND-ORDER.md. The loop and the hub→switch change — the peer's other examples — are built. | "initiate a DDoS... creating a loop", and the safety outcome |
| P12 | A **non-interactive DoS explainer** was later added at Sam's request (SECOND-ORDER row 16): the "storm" chapter's `flood` level. Ordinary hosts flood one server, its single link saturates, most frames drop; the student watches and answers a quiz. No edits, no spoofing, no student-driven attack — just the existing finite-queue rule under honest traffic, so it is not the mechanic P11 blocked and was not built to evade the stop. Explainer levels use the always-true `observe` goal. | "a game that... visualizes packets", the DoS request, and the safety outcome |
| P13 | Each teaching chapter gains a second, harder tier of three missions (SECOND-ORDER row 17), ramping to one technical finale, in which the student configures a larger network — more machines, more hops, more loops — by click-choice only (no typed addresses). Link: `crowd`, `backbone`, `floor`. Network: `point`, `roads`, `across`. Transport: `window`, `connect`, `reliable`. No new core mechanic: each is the existing deterministic engine on a bigger topology with more `edits`, one wrong choice anywhere failing the goal. Nineteen levels, 57 stars. | "make some levels more interactive", "ape the correct behaviour", "vary machines, hops, switches", "keep it gamified until the finale" (Sam) |
| P14 | The map can be zoomed for accessibility (SECOND-ORDER row 18): a range slider (plus `+`/`−` and reset) drives a `--zoom` CSS variable scaling the backdrop and SVG together, and the frame scrolls when enlarged. Every zoom number lives in HTML attributes and CSS; `app.js` only reads the slider value and calls `stepUp()`/`stepDown()`, so the page stays free of numeric literals (Builder D3) and writes no inline style (CSP). | "make sure the rendering window can be made larger / smaller or that it's easy to zoom in and out for accessibility" (Sam) |
