| 19 | F | A student reported playback "instantly resolving" on *Split the crowd* — no animation, straight to the result. The map, glyphs and per-tick motion were all fine on the live site in Chromium, Firefox and WebKit; the cause was the classic `requestAnimationFrame` catch-up gap. The loop advanced `cur.ms` by the real wall-clock `dt` since the last frame, and when the tab lost focus, the window was switched, or the machine hitched between pressing Run and the first frame, rAF handed back one enormous `dt` — so `cur.ms` leapt past the whole run in a single frame and `frame()` returned `done` at once. Reproduced by wrapping `requestAnimationFrame` to report +10 s per frame: the HUD jumped from Tick 0 to Tick 12 on the first frame. Fixed in `web/app.js` by capping a frame's advance at one tick (`if (dt > mpt()) dt = mpt();`, the cap coming from `data/display.json` so the page stays number-free) — a focus gap now resumes from where it paused instead of skipping. **A follow-up report ("the first run is fixed, every run after still skips") exposed the deeper cause: `dt` could also go *negative*.** An animation frame's timestamp can precede the `performance.now()` captured when playback started — a real, timing-dependent browser quirk, more likely on a re-run — so `dt = now - cur.last` came out below zero, `cur.ms` went negative, and the negative JS number handed to the core's `frame(ms: u32)` wrapped to ~4.29 billion (`(-5) >>> 0 === 4294967291`), which clamped to the run's end and fired `done` on that one frame. One such frame skipped the whole run, and because it happens on the first frame it looked deterministic per environment. Proven by making a run's first rAF timestamp 50 ms in the past: the HUD jumped straight to the final tick with the overlay up. Fixed by clamping `dt` on *both* sides — `if (dt < 0) dt = 0;` as well as the one-tick cap (0 is an allowed literal) — so `cur.ms` is monotonic and never negative. While there, the animation loop was made single-instance: pressing Run five times quickly had stacked five concurrent rAF loops (measured 300 callbacks/s; a shared `cur.last` kept the *speed* right so it only wasted CPU) — a stored handle now lets each run/replay/play cancel the previous loop (back to ~60/s). Verified by Playwright against the local build and by `scripts/check.sh` in all three engines. |
